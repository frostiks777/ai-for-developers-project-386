## Шаг: Первая фича — главная страница

Цель: пройти полный цикл на небольшой задаче (главная страница, которая рассказывает про сервис и ведёт на запись).

- Цикл начинается с разговора: `/grill-with-docs` — интервью + складывание документов предметной области.
- На выходе: словарь проекта в `CONTEXT.md` и решения в `docs/adr/`.
- Дальше `/implement` — код вместе с тестами, ревью, коммит.

Требования:
- Главная страница открывается и ведёт на страницу записи.
- Есть тесты на главную страницу, прогон в GitHub Actions зелёный.
- В репозитории есть `CONTEXT.md` со словарём проекта.
- Принятые решения записаны в `docs/adr/`.

Задачи:
1. Вызвать `/grill-with-docs` и пройти интервью по главной странице.
2. Проверить, что в `CONTEXT.md` появился словарь, а в `docs/adr/` — решения.
3. Вызвать `/implement` и реализовать страницу вместе с тестами.
4. Убедиться, что прогон в GitHub Actions зелёный.

Статус: `[x] выполнено` (2026-09-24): создан `CONTEXT.md` (словарь проекта), [ADR-0010](adr/0010-landing-and-booking-routes.md); главная `/` — лендинг, бронь перенесена на `/book/:slug`; тесты и CI зелёные.

## Шаг: Проектирование бронирования (карта решений)

Основная функциональность: типы встреч, календарь свободных слотов, бронирование и список встреч владельца. Работы на несколько сессий — проектируем картой решений.

- Начать с `/wayfinder` — карта в трекере: одна задача + дочерние задачи-вопросы (сущности контракта, модель слотов, конфликт типов встреч, границы тестирования).
- Пункт назначения карты: «утверждённая спецификация приложения, по которой можно раскладывать тикеты».
- **Design First**: сначала фиксируем поведение и API-контракт, потом фронтенд и бекенд раздельно.
- Контракт — TypeSpec; OpenAPI генерируется из него.
- Из OpenAPI: клиентский SDK для фронта + серверные артефакты (типы, проверка запросов, заготовки маршрутов).
- Цепочка: `TypeSpec → OpenAPI → { клиентский SDK (фронт); типы/валидация/маршруты (бэк) }`.
- Руками не писать то, что описано в контракте; команды генерации — одной командой (Makefile/скрипты).

Что должно уметь приложение (роли — владелец и гость, без регистрации/авторизации):
- Владелец: создавать типы событий (id, название, описание, длительность в минутах); видеть страницу предстоящих встреч всех типов.
- Гость: смотреть виды брони (название, описание, длительность); выбрать тип события, открыть календарь, выбрать свободный слот в ближайшие 14 дней; создать бронирование.
- Занятость: на одно время нельзя две записи, даже для разных типов событий.
- Окно записи: 14 дней от текущей даты.

Спецификация и тикеты:
- `/to-spec` — синтез спецификации из уже обсуждённого (запускать в сессии с картой в контексте): пользовательские истории, решения по реализации и тестированию.
- `/to-tickets` — вертикальные тикеты (контракт → сервер → интерфейс → тесты) с объявленными зависимостями.

Требования:
- В трекере есть карта решений; задачи закрыты с записанными ответами.
- В трекере есть спецификация с пользовательскими историями и решениями по тестированию.
- В трекере есть тикеты с зависимостями.
- В репозитории есть TypeSpec-контракт (сценарии владельца и гостя).
- OpenAPI генерируется из TypeSpec; команда генерации описана в репозитории.
- Клиентский SDK генерируется из спецификации.
- Серверные артефакты генерируются из спецификации.
- Генерация повторяется одной командой, сгенерированное руками не правится.

Статус: `[ ] не начато`.

## Шаг: Реализация тикетов

- `/implement` по тикетам; фронтир — тикеты без незакрытых блокирующих.
- `/implement` сам пишет тесты на границах из спецификации, прогоняет типы/тесты, проходит ревью и коммитит.
- Основной сценарий проверяется в браузере (рекомендуется Playwright).
- Правила бронирования — на сервере (проверка только в UI обходится прямым запросом в API).
- Обращения к API — через сгенерированный SDK (не `fetch` руками). При смене контракта: правка TypeSpec → генерация → код обеих сторон.

Требования:
- Сквозной сценарий гостя: выбор типа, календарь, запись на свободный слот, подтверждение.
- Занятый слот не предлагается как свободный; повторная запись не проходит (в т.ч. для другого типа).
- Правила бронирования выполняются на сервере.
- Есть страница владельца со списком предстоящих встреч всех типов.
- Реализация совпадает с контрактом (пути, методы, поля, коды).
- Фронтенд ходит в API через сгенерированный SDK.
- Тесты покрывают основной сценарий и конфликт слотов; CI зелёный.

Статус: `[ ] не начато`.

## Критерии приёмки проекта («Как мы проверяем проект»)

Автопроверка (`hexlet-check.yml`) собирает `Dockerfile` и проверяет ответ на главной. Контракт, бронирования, тесты и трекер автопроверка не смотрит — их оценивает наставник по зонам ниже. Ключевой формат: разработка ведётся ИИ-агентом (в идеале ни строки вручную).

### Функциональность
- Сценарий записи целиком: тип встречи → календарь → свободный слот → запись → подтверждение.
- Занятый слот повторно не бронируется (в т.ч. через другой тип), понятное сообщение о конфликте.
- Правила бронирования выполняются на сервере.
- Страница владельца со встречами всех типов в одном списке.
- API отвечает по контракту; OpenAPI из TypeSpec → клиентский SDK и серверные артефакты.
- Окно записи 14 дней, слоты по 30 минут.
- Сборка в образ, авто-старт, порт из `PORT`, ссылка на сервис в `README.md`.

### Проверяемость
- Тесты и линтер в GitHub Actions, прогон на основной ветке зелёный.
- Тесты покрывают сценарий бронирования и конфликт слотов.
- Conventional Commits; release-please создаёт release-PR.
- Секретов в репозитории нет.

### Настройка агентной разработки
- `AGENTS.md` с командами запуска/тестов/линтера и правилом про коммиты.
- `docs/agents/` с конфигурацией трекера (после `/setup-matt-pocock-skills`).
- Конфигурация MCP-серверов в репозитории.
